# VerseKit Org Standard v1 integration architecture (VK-01)

Status: architecture and implementation record, updated 17 November 2026. VK-02 and VK-03 authentication infrastructure are implemented on `codex/vk-03-versekit-device-auth`; this does not mean any VerseKit data scope is operational, discovery is live, or any image has been deployed. Source architecture baseline: `compumark/verselink` `5ce1758b79b16a83c7a19e81fa48b841cb1b9903`; [Issue #140](https://github.com/compumark/verselink/issues/140) is the architecture decision record. Contract: [v1 OpenAPI](https://github.com/Xharig/VerseKit/blob/main/tools/orga-standard/v1/openapi.yaml), [standard README](https://github.com/Xharig/VerseKit/blob/main/tools/orga-standard/README.md), and [client discovery parser](https://github.com/Xharig/VerseKit/blob/main/crates/versekit-core/src/orgstd/discovery.rs).

## Decisions and boundary

Use Variant A: `src/integrations/versekit/` as an optional Node.js ESM adapter inside the existing server. The implementation uses a guarded bootstrap/router mount and narrowly scoped dependencies passed to it. No core business-logic refactor, new group administration, or second org database. `VERSEKIT_ENABLED` is true only for the literal `true`; absent, false, or malformed values leave all VerseKit routes unavailable, start no VerseKit jobs, do no VerseKit token work, and require no VerseKit tables. The adapter does not initialize when disabled. Existing `/api/*`, `/healthz`, login, groups, inventory, orders, telemetry and UI retain their behavior. Enabled mode validates a UUID `VERSEKIT_GROUP_ID`, an existing group, and an absolute `VERSEKIT_PUBLIC_URL` with HTTPS, no credentials, query or fragment, and the intended public origin. Invalid enabled configuration fails startup closed, without partial routing or background work. These settings are implemented for the optional adapter; operational data capabilities remain disabled.

The adapter shares VerseLink's Node.js process. Its initialization must finish before routes are exposed; initialization failure must fail closed without partially changing application state. Expected adapter errors return the standard OAuth or problem response, while existing routing and the global error handler remain intact. Bound request bodies, execution time and resource use; avoid blocking work and unbounded allocation in handlers. Any future cleanup must have caught promises, bounded work and a shutdown path; no unhandled background jobs. Test that recoverable adapter errors leave existing routes and `/healthz` usable and that disabled mode never initializes the adapter. Process-level crashes or resource exhaustion can still affect all of VerseLink; this design does not provide crash isolation.

The stock client discards an entered URL path (`discovery.rs`, `Origin::parse`); the user enters the existing HTTPS VerseLink host. Serve `/.well-known/versekit-org.json` there; advertise the same configured origin for `/versekit/v1`, `/versekit/v1/device/code`, `/versekit/v1/token`, `/versekit/v1/revoke`, and bare `/device`. Never derive canonical URLs from `Host` or `X-Forwarded-*`. Confirm the reverse proxy passes the well-known and `/device` paths and HTTPS externally. No group path or client group picker. Reserve `/device` for the approval page only when enabled and verify there is no route collision before mounting. Discovery must remain unavailable until at least one recognized, tested read scope and endpoint is ready: the current client rejects an empty `scopes_supported` list. `org.name` comes from the configured group's name, `tag` only if a valid existing value is available; omit otherwise. Do not expose internal group UUID in discovery.

Each adapter instance binds to exactly one existing `blueprint_groups.id`. On **every** protected request, including `/me`, resolve a hashed Bearer token, check validity, expiry and revocation, require `token.group_id === configured VERSEKIT_GROUP_ID`, `VERSEKIT_ENABLED=true`, `app_users.account_status='active'`, `group_members(group_id=VERSEKIT_GROUP_ID, app_user_id=token.user_id)`, and the endpoint's granted scope (except `/me`, which needs no scope). Apply the same group-binding and validity checks to refresh and every operation that extends or reuses a grant. Every domain query must carry the configured group predicate, even if a user also belongs to another group. Never accept `group_id` from a VerseKit request. Changing the configured group immediately rejects grants bound to the former group; members of both groups must authorize again. A removed member, deactivated account, disabled integration, or deleted group loses access immediately; also reject refresh and consent. A member of another group alone has no access. The existing VerseLink multi-group and invitation flows remain unchanged (`src/server.js` schema around lines 268–290; `/api/orders` around 2185).

## Exact v1 path and domain mapping

The twelve paths below are the OpenAPI paths, including the browser page. Status records distinguish implemented authentication infrastructure from future domain API work. Domain collection reads use v1 cursor paging (`limit` 1..1000, default 500; stable keyset cursor bound to group/filter/scope, invalid cursor `400 INVALID_CURSOR`) and Bearer authentication unless noted; `/me` is a single identity response.

| Method and path | Scope / contract | VerseLink source and mapping | Status / gate |
| --- | --- | --- | --- |
| `GET /.well-known/versekit-org.json` | Public `standard`, `org`, version `1` endpoints and `scopes_supported` | `blueprint_groups.name`; configured public URL; only proven scopes | Planned; publish only with working auth and at least one scope |
| `POST /versekit/v1/device/code` | Public form `client_id`, space-separated `scope`; `device_code`, `user_code`, bare `verification_uri`, `expires_in`, `interval` | Dedicated integration grants; known scope intersection; no invite or telemetry code reuse | Implemented; scope readiness enforced |
| `POST /versekit/v1/token` | Public form device-code or refresh grant; Bearer, `expires_in <= 3600`, rotated refresh, granted `scope` | Dedicated hashed grants/tokens linked to the originating grant, `app_users.id` and fixed group | Implemented; RFC 8628/OAuth errors; replay revokes token family |
| `POST /versekit/v1/revoke` | Public form `token`, optional hint/client; always 200 for unknown token | Dedicated transactional token-family revocation | Implemented; RFC 7009 behavior |
| `GET /device` | Bare browser confirmation page, no code in URL | Existing `dashboard_sessions`/`app_users` login; manually entered code and consent | Implemented; protected form POST, session-bound CSRF and one-time consent challenge |
| `GET /versekit/v1/me` | Bearer, no scope; `{member:{id,name},org:{name},scopes}` | `app_users.id`, `COALESCE(verselink_name,display_name)`; configured group name; stored grants | Implemented; fixed-group and live account/membership validation |

| `POST /versekit/v1/orders/{orderId}/deliveries` | `orders:write`; `Idempotency-Key` 1..200, nonempty `items`, 201 `delivery_id` and updated `order` | Existing `/api/orders/action` `report` inserts one delivery into `material_order_deliveries` | Blocked until atomic reuse/serialization and semantic review; no direct bypass |

Six and only six standard scopes are `orders:read`, `orders:write`, `stock:read`, `stock:write`, `blueprints:read`, `blueprints:write`. Initial candidate set: the three reads, **independently** validated and advertised only after their contract/security tests pass. `orders:write` has a separate gate. Both snapshot write scopes are unsupported for the initial release. Basetool Exchange is background comparison only: its DPoP/Keycloak/registry features and other nonstandard client requests are outside v1 and are not inherited into this adapter.

Wire shape checklist for implementers: device-code request is `application/x-www-form-urlencoded` with required `client_id` and space-delimited `scope`; its JSON response requires `device_code`, `user_code`, `verification_uri`, `expires_in` and optionally `interval` (default 5). Token request is form data with either `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `device_code`, `client_id`, or `grant_type=refresh_token`, `refresh_token`, `client_id`; JSON success requires `access_token`, `token_type=Bearer`, `refresh_token`, with optional `expires_in` and `scope`, plus `Cache-Control: no-store`. Revoke requires form `token`, optionally `token_type_hint` and `client_id`, and returns 200 even when unknown. `/me` requires `member.id`, `member.name` and `scopes`, with optional `org.name`/`org.tag`. Stock GET requires `items`; each item requires `item` and nonnegative `quantity`, and may carry `unit`, `quality` (integer 0..1000), `location` and read-only `member`. Stock PUT requires `items` of at most 5000 stock items and returns `items_stored`. Blueprint GET requires `blueprints`; each entry requires `name` and `holders` (string array). Blueprint PUT requires at most 10000 nonempty names of at most 200 characters and returns `blueprints_stored`. Orders GET requires `orders`; every order requires `id`, `title`, `status` (`open/done/cancelled`), and `items`; every item requires `item`, `quantity`, `delivered` and may have `unit`. Delivery POST requires an `Idempotency-Key` header and JSON `{items:[{item,quantity}]}` with at least one positive-quantity item; success is 201 with `delivery_id` and `order`. The three list responses may include `next_cursor` (string or null). Enforce field length limits from OpenAPI for names, locations, notes and keys; do not use this checklist in place of schema-based conformance tests.

## Field, precision and visibility rules

**Orders.** `material_orders.id` is the stable v1 `id`; `order_number` and `material_name` can form a title (no new title state). One VerseLink order has one material, so v1 `items` has one entry with `item=material_name`, `quantity=required_quantity`, and `delivered` from the delivery ledger where present, otherwise the legacy `delivered_quantity` fallback used in `/api/orders` (lines 2185–2211). Do not sum ledger and fallback. The existing `quantity_unit` is free text, default `SCU`; normalize only known `SCU`→`scu`, `CSCU`→`cscu`, and piece-equivalent values→`piece`. Unknown units block advertising `orders:read` until a documented safe handling policy is chosen; never silently label them `piece`. PostgreSQL `numeric` is not bounded to a fixed scale: define accepted precision and JSON conversion with fixtures before shipping. Status mapping: `cancelled`→`cancelled`, `completed` or verified full delivered total→`done`, `open`/`claimed`/`reported`→`open`; the latter loses work-in-progress detail, which v1 cannot express. Do not mark a partially delivered order done. `note` may come from `material_orders.note` after length/privacy review. There are no order destination or due-date columns: omit `location` and `due`. `required_quality` and `delivered_quality` have no v1 order field. Keep hidden orders hidden and never expose other groups (`src/server.js` lines 291–325, 744–752, 2185–2211, 2849–2866).

**Stock.** Group stock is a ledger, not a member's personal inventory. Existing `materialInventoryNetRows` groups by member, case-insensitive material name, band, exact quality and source location and subtracts withdrawals; its `Number(...)` arithmetic is a precision risk requiring SQL numeric/keyset verification (`src/server.js` lines 387–403, 2646–2677). Export positive net quantities only, in `scu`, with `quality_value` 1..1000 (the standard also accepts zero, but VerseLink has no zero quality), `source_location` only when present, and a member identity allowed by the agreed visibility policy. `reported`, `deposited` and `in_refinery` cannot be represented as stock fields; decide which states count as shareable before claiming conformance. The group matrix currently aggregates away member, quality and location, so it cannot directly serve v1. The separate `user_inventory` uses integer `quantity`, item catalog UUID/name, location UUID/name, trade status and privacy settings (`PRIVATE/GROUPS/PUBLIC`); it is not automatically group stock. Never export private personal inventory merely because two users share a group. The chosen stock read source needs owner consent and explicit privacy tests (lines 552–589, 1949–1992, 2755–2776).

**Blueprints.** SCMDB is the ownership source: `member_blueprints(token_hash,tag)` plus connected/unrevoked `scmdb_connections`, `app_users`, configured group membership, and optional `reference_blueprints.product_name`. Use stable tag internally for deduplication, but v1 exposes only `name` and holder strings. Decide deterministic English display name and collisions among tags; do not invent a VerseKit blueprint ID. Holders use active group member display names only and respect visibility policy. Existing `accessibleBlueprintQuery` permits *any* shared group; it must not be reused unmodified for the fixed-group adapter. `publicBlueprintQuery` has a fixed-group join but lacks the connected/revoked filter, so also needs adaptation. No SCMDB sink token is a VerseKit credential (`src/server.js` lines 452–511, 1170–1213, 1350–1380, 1925–1932).

## Device grant, errors and threat model

The user enters the existing host, selects Connect, receives a temporary code from VerseLink, opens `/device`, logs in through the existing VerseLink session, types the code, and approves individually selected requested scopes. No registration or automatic consent. The server stores only keyed hashes of random device/access/refresh secrets (and a slow hash or keyed lookup plus attempt limits for the short user code), grant state, requested/granted scopes, immutable user/group binding, expiry and rotation/revocation timestamps. Use a transaction and row lock for one-time code exchange and refresh rotation; concurrent/replayed refresh invalidates the token family. Device code expires (proposed 600 seconds), polling begins at `interval` (default 5 seconds) and increases on `slow_down`; access tokens live at most 3600 seconds. Refresh and any grant extension recheck token validity, revocation, active account, current membership, enabled configuration, granted rights, and the stored group against the configured group. A group switch cannot transfer authorization; old grants are denied immediately and the new group requires fresh consent. Revocation of a refresh token ends its access tokens. Use separate integration-only tables; do not reuse `auth_tokens`, `dashboard_sessions`, `telemetry_pairing_codes`, `group_invites`, or `scmdb_connections` as VerseKit token/grant storage. Existing `dashboard_sessions` remain the browser login session for the approval page.

The confirmation GET has no code in URL. Form POST requires the existing authenticated session, same-origin/CSRF token, deliberate scope selection, fixed-group membership and active account. Escape displayed org/member text. Rate-limit code creation, polling, manual code attempts and token operations by safe client key plus code/grant/account as appropriate; avoid relying on untrusted forwarding headers. Protect against user-code guessing, phishing via forged origin, cross-group data leakage, refresh replay, scope escalation, idempotency replay and log leakage. Log request ID, outcome and opaque grant ID only; never log user/device codes, tokens, cookies, inventory detail or personal notes. Retain/purge grants under a documented period. `verification_uri` must be bare; never put the user code into it. TLS termination at Cloudflare/reverse proxy must preserve the configured public HTTPS origin.

API errors use `application/problem+json` with `status` and stable `code` from the OpenAPI set: `UNAUTHORIZED`, `SCOPE_MISSING`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `INVALID_BODY`, `INVALID_CURSOR`, `IDEMPOTENCY_KEY_MISSING`, `ORDER_CLOSED`, `ITEM_NOT_IN_ORDER`, `RATE_LIMITED`, `MAINTENANCE`, `INVALID_REQUEST`; use `WWW-Authenticate: Bearer error="invalid_token"` on 401 and integer `Retry-After` on 429/503. Device/token grant failures use form-OAuth JSON errors (`authorization_pending`, `slow_down`, `access_denied`, `expired_token`, `invalid_grant`, `invalid_scope`, `unsupported_grant_type`), not problem JSON. Unknown scope names are dropped at device-code creation; if none remain, return `invalid_scope`. Unknown fields are ignored as the v1 contract specifies. Validate method, content type, body size and schema. Do not advertise a scope with placeholder responses.

For future `orders:write`, require a persistent atomic idempotency record whose replay identity is the authenticated member plus `Idempotency-Key` within the fixed adapter namespace. The requested order ID and canonical request body belong in the fingerprint, not the replay identity; store the first response. The same member/key/request returns the first result without booking again, including after restart. The same member/key with a different order or body never books another delivery. The OpenAPI does not specify a precise mismatch response; choose an existing v1 error code/status during the VK-06 protocol review rather than inventing a code. Transactions and uniqueness/locking must serialize concurrent requests. Bind records to the configured group and deny old grants after a group switch; old idempotency records cannot authorize or be replayed into the new group. Lock the order and key before booking, validate requested material against the single order item, positive quantity, remaining amount, unit/precision, status and membership *inside the transaction*, then reuse the authoritative reporting side effects. The current `/api/orders/action` reads before its transaction and has no idempotency key; a second handler copying its SQL would permit races and bypass behavior. `claimed`/`reported` orders accept reports today although v1 says “open order”; this and the mapping above need an explicit owner decision. Until Issue #145's feasibility and safety gates pass, do not advertise `orders:write`.

## VK-02 foundation status

The VK-02 implementation adds an exact, case-sensitive opt-in: `VERSEKIT_ENABLED=true`. Every other value, including an absent flag, leaves the adapter unloaded and VerseLink routes/startup unchanged. When enabled, `VERSEKIT_GROUP_ID` must be one existing UUID in `blueprint_groups` and `VERSEKIT_PUBLIC_URL` must be an explicit HTTPS origin with no credentials, query, fragment or path beyond `/`. Validation checks the original authority before URL parsing: empty or zero ports, legacy/ambiguous IPv4 spellings, encoded separators and malformed hostnames fail. Conventional IPv4, bracketed IPv6 and valid DNS/IDN hosts are accepted; hostname case and IDN are canonicalized, an explicit default `:443` and optional trailing slash are removed, and other valid ports are retained. Validation and group lookup finish before the server listens; invalid settings stop startup. Public URLs come only from this configuration, never request headers. No new schema, token handling or background job is introduced.

At the VK-02 phase boundary the adapter reserved root `/.well-known/versekit-org.json`, `/versekit/v1` and its descendants, and `/device` only while enabled. VK-02 had **zero operational scopes** and all reserved routes returned 404. The current VK-03 implementation adds device authorization, browser consent, token lifecycle and `/me`, but still has **zero operational data scopes**: live discovery and data endpoints remain unavailable. Runtime environment variables cannot activate a scope. A completed and tested read scope (VK-05, VK-07 or VK-08) is required before discovery can become live. Adapter errors are bounded to reserved routes; a fatal Node.js process failure remains a shared-process risk.

VK-02 tests cover disabled mode, strict configuration, group existence, the discovery builder, reserved routing and unavailable endpoints. When `TEST_DATABASE_URL` points to the guarded loopback `verselink_test` database, the integration test creates a disposable schema, uses the real `blueprint_groups` table and spawned HTTP server, verifies enabled and disabled routing, and checks failed enabled startup. It skips locally when no test database is configured; the existing PostgreSQL CI service supplies one. Later phases must add real-client, reverse-proxy/Cloudflare and contract tests before advertising capabilities.

## VK-03 authentication implementation status

VK-03 implements optional OAuth infrastructure while leaving all operational data scopes disabled in normal runtime. `VERSEKIT_ENABLED` must be the exact string `true`; the enabled adapter validates one existing configured group and initializes only VerseKit-specific tables. There is no environment setting that enables capabilities. The adapter's capability argument is an internal constructor seam for isolated tests; production startup does not pass it and therefore has zero operational scopes. Device-code requests for unavailable scopes fail with `invalid_scope`, and discovery remains unavailable. This is not full VerseKit connectivity.

Device authorization uses random device/user codes and stores only purpose-separated HMAC hashes. The existing VerseLink `bp_session` and active `app_users` account authenticate `/device`; code entry is POST-only, rate limited, CSRF and same-origin protected. Consent displays only requested capabilities enabled on that adapter, starts with all permissions unchecked, and binds a single-use approval challenge to the member and browser-session hash. Approval or denial locks the challenge and grant rows, revalidates active account and configured-group membership, and performs a one-time state transition. No device or bearer credentials are displayed in the browser.

Token families retain the originating device-grant ID, fixed client, member, configured group and approved scope subset. Access and refresh tokens are stored as keyed hashes. Refresh uses a transaction and row locks, rotates the refresh credential, preserves scopes, and rechecks grant, account and group state. Concurrent or replayed refresh use cannot issue two successful rotations; use of a consumed refresh token revokes the family. `/versekit/v1/revoke` follows public-client RFC 7009 behavior: unknown credentials return an empty 200 response, while a known access or refresh token revokes its complete family and all family tokens transactionally. `/versekit/v1/me` authenticates only with a VerseKit Bearer access token, verifies the originating consumed grant and live token, account, group and membership on every request, and returns only member ID/name, configured organization name and stored approved scopes. Browser cookies do not authorize it.

All VerseKit form endpoints (`POST /versekit/v1/device/code`, `/versekit/v1/token`, `/versekit/v1/revoke`, and browser `POST /device`) share an 8 KiB maximum body and a 10-second total body-reading deadline. An oversized declared `Content-Length` is rejected before reading; a streamed body is rejected as soon as it crosses the limit. These cases return HTTP 413 with `Connection: close`; stalled bodies return HTTP 408 with the same close behavior. The reader pauses request consumption, flushes the response, then closes the socket, so rejected uploads are not drained and the connection is not reused. Client disconnects and stream errors settle the pending read without parsing or changing grant/consent state; request timers and data listeners are cleared. The limit, deadline and behavior apply only to VerseKit form endpoints; they do not change global VerseLink HTTP timeouts. Form content type, duplicate-field checks, CSRF, same-origin, session and rate-limit checks remain enforced.

Requests rejected before form parsing (including unsupported methods, unexpected query strings, invalid consent origins and rate limits) pause the unread request, return the existing rejection with `Connection: close`, then close the socket after the response flushes. A bounded fallback closes connections if response flushing fails; rejected uploads are never drained or reused.

Device-grant storage is capped globally at 10,000 retained grants. Every creation transaction takes the same PostgreSQL transaction-scoped advisory lock, counts all retained grant states, and inserts only below the cap. Capacity exhaustion fails closed with OAuth `temporarily_unavailable`, HTTP 429 and `Retry-After: 900`; cleanup frees capacity under the same lock coordination as new admissions. The limit applies across adapter instances sharing the database and is not environment-configurable.

VK-03 supplies authentication and connection lifecycle only. VK-04 remains responsible for the broader central authorization/scope enforcement layer; VK-05, VK-07 and VK-08 must implement and test individual data scopes before any are advertised. VK-06 remains conditional and is not required for the read-only MVP. VK-09 remains responsible for real-client, conformance and DEV validation. No deployment, image publication, discovery activation or business-data endpoint is implied by this implementation status.

Credential retention: token families have a fixed 180-day absolute lifetime; refresh never extends it and credentials expire no later than that boundary. Family/grant/token history is retained until seven days after family expiry to preserve refresh replay detection, then the family cascade removes its credentials. Orphanable expired pending, denied, or consumed grants are retained 30 days. Consent challenges are removed one day after expiry or consumption. Expired access-token rows are independently eligible for removal. The enabled adapter schedules cleanup every 15 minutes, in batches capped at 200 rows per record category, using PostgreSQL `SKIP LOCKED` and transactions so multiple instances can run safely. Runs do not overlap within an instance; failures are caught and retried by the next interval with only safe error metadata logged. Disabled mode creates no VerseKit tables or cleanup timer. Active refresh tokens and families are not cleanup candidates.

## Global device-grant admission and retained storage

Enabled instances sharing PostgreSQL use one persistent global token bucket: production capacity is 24 grants, refilled continuously from PostgreSQL time at one token per 3600 seconds. Initialization persists capacity and refill interval; later initializations validate the stored policy and fail on conflict without resetting balance or timestamp. Grant creation takes a PostgreSQL transaction-scoped advisory lock, refills and consumes a token, checks the global retained-grant count, then inserts within the same transaction. Failed admission rolls back token consumption. The existing per-IP limiter is additional protection, not a substitute for the database-wide limit. At most 10,000 retained device grants are admitted. HTTP capacity rejection returns 429, `Retry-After` (900 seconds for the storage ceiling; a calculated positive delay for an empty bucket), and `temporarily_unavailable`.

Cleanup can restore storage capacity: expired orphanable grants are eligible after 30 days beyond grant expiry; a grant referenced by a retained token family remains until family cleanup. Cleanup runs every 15 minutes in bounded batches. Disabled mode does not initialize the adapter, quota table, or cleanup job.

### Availability limits and retention estimate

The shared bucket is a finite availability resource: an attacker who can reach the endpoint can exhaust its current balance and temporarily prevent legitimate new device authorizations until refill. This does not invalidate existing access tokens or make refresh and revocation depend on new-grant admission; those operations do not consume new-grant tokens. The bucket and IP limiter reduce abuse but do not eliminate denial-of-service risk.

For a healthy-operation estimate, a grant can exist for up to 10 minutes before its token family is created. The family then has a fixed 180-day absolute lifetime, followed by seven days of replay-history retention and at most 15 minutes until scheduled cleanup: approximately 187.0174 days total. At one grant per hour, plus the initial 24-token burst, a conservative estimate is `24 + ceil(24 × 187.0174) = 4,513` retained grants. Orphanable grants have the shorter bound of a 10-minute grant lifetime, 30 days post-expiry retention, and up to 15 minutes of cleanup delay; at the same issue rate this is below the family-backed estimate. This estimate assumes cleanup continues to run and no administrator or other process disables it. It is not an absolute database-size guarantee: prolonged cleanup outages, operational changes, or unusual retained records can allow storage to grow until the 10,000-grant admission ceiling rejects new grants.

## Upstream v1 compatibility: capacity errors

The reviewed upstream contract is the VerseKit v1 OpenAPI at [the pinned upstream revision](https://github.com/Xharig/VerseKit/blob/10438c39aa1fb6bd4901483c51b4ce5b4d00bf9f/tools/orga-standard/v1/openapi.yaml) (blob `10438c39aa1fb6bd4901483c51b4ce5b4d00bf9f`). The contract's general API description mentions HTTP 429 and 503 with `Retry-After`; the device-code operation explicitly lists 200 and 400, and its `OAuthError` enum does not include `temporarily_unavailable`.

Accordingly, the implementation's 429 status and positive `Retry-After` align with the general error guidance, but `{ "error": "temporarily_unavailable" }` is outside the published enum, and 429 is not explicitly listed among that operation's responses. A strict schema-validating client may reject either discrepancy. The other listed OAuth errors are not suitable substitutes: `invalid_request`, `invalid_scope`, and grant-state errors would misrepresent a temporary capacity condition. This is a confirmed schema mismatch; client rejection is a compatibility risk inferred from strict validation, not a demonstrated behavior of every client. Resolve it through an upstream specification clarification or explicit extension before claiming full conformance. Keep the current response documented as a known compatibility limitation; it does not by itself block VK-03 commit approval, but it must be addressed before claiming strict contract conformance or enabling broad discovery.
