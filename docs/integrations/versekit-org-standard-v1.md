# VerseKit Org Standard v1 integration architecture (VK-01)

Status: architecture and implementation record, updated 19 November 2026. VK-02 through VK-04 authentication infrastructure is implemented. VK-05 adds the fixed-group `orders:read` endpoint and discovery capability; PostgreSQL 16 verification is pending in this environment. VerseKit remains disabled unless `VERSEKIT_ENABLED=true`, and no image has been deployed. Source architecture baseline: `compumark/verselink` `5ce1758b79b16a83c7a19e81fa48b841cb1b9903`; [Issue #140](https://github.com/compumark/verselink/issues/140) is the architecture decision record. Contract: [v1 OpenAPI](https://github.com/Xharig/VerseKit/blob/main/tools/orga-standard/v1/openapi.yaml), [standard README](https://github.com/Xharig/VerseKit/blob/main/tools/orga-standard/README.md), and [client discovery parser](https://github.com/Xharig/VerseKit/blob/main/crates/versekit-core/src/orgstd/discovery.rs).

## Decisions and boundary

Use Variant A: `src/integrations/versekit/` as an optional Node.js ESM adapter inside the existing server. The implementation uses a guarded bootstrap/router mount and narrowly scoped dependencies passed to it. No core business-logic refactor, new group administration, or second org database. `VERSEKIT_ENABLED` is true only for the literal `true`; absent, false, or malformed values leave all VerseKit routes unavailable, start no VerseKit jobs, do no VerseKit token work, and require no VerseKit tables. The adapter does not initialize when disabled. Existing `/api/*`, `/healthz`, login, groups, inventory, orders, telemetry and UI retain their behavior. Enabled mode validates a UUID `VERSEKIT_GROUP_ID`, an existing group, and an absolute `VERSEKIT_PUBLIC_URL` with HTTPS, no credentials, query or fragment, and the intended public origin. Invalid enabled configuration fails startup closed, without partial routing or background work. `orders:read` is the only operational data scope; all other data scopes remain disabled.

The adapter shares VerseLink's Node.js process. Its initialization must finish before routes are exposed; initialization failure must fail closed without partially changing application state. Expected adapter errors return the standard OAuth or problem response, while existing routing and the global error handler remain intact. Bound request bodies, execution time and resource use; avoid blocking work and unbounded allocation in handlers. Any future cleanup must have caught promises, bounded work and a shutdown path; no unhandled background jobs. Test that recoverable adapter errors leave existing routes and `/healthz` usable and that disabled mode never initializes the adapter. Process-level crashes or resource exhaustion can still affect all of VerseLink; this design does not provide crash isolation.

The stock client discards an entered URL path (`discovery.rs`, `Origin::parse`); the user enters the existing HTTPS VerseLink host. Serve `/.well-known/versekit-org.json` there; advertise the same configured origin for `/versekit/v1`, `/versekit/v1/device/code`, `/versekit/v1/token`, `/versekit/v1/revoke`, and bare `/device`. Never derive canonical URLs from `Host` or `X-Forwarded-*`. Confirm the reverse proxy passes the well-known and `/device` paths and HTTPS externally. No group path or client group picker. Reserve `/device` for the approval page only when enabled and verify there is no route collision before mounting. Discovery requires at least one recognized read scope; VK-05 exposes only `orders:read`. `org.name` comes from the configured group's name, `tag` only if a valid existing value is available; omit otherwise. Do not expose internal group UUID in discovery.

Each adapter instance binds to exactly one existing `blueprint_groups.id`. On **every** protected request, including `/me`, resolve a hashed Bearer token, check validity, expiry and revocation, require `token.group_id === configured VERSEKIT_GROUP_ID`, `VERSEKIT_ENABLED=true`, `app_users.account_status='active'`, `group_members(group_id=VERSEKIT_GROUP_ID, app_user_id=token.user_id)`, and the endpoint's granted scope (except `/me`, which needs no scope). Apply the same group-binding and validity checks to refresh and every operation that extends or reuses a grant. Every domain query must carry the configured group predicate, even if a user also belongs to another group. Never accept `group_id` from a VerseKit request. Changing the configured group immediately rejects grants bound to the former group; members of both groups must authorize again. A removed member, deactivated account, disabled integration, or deleted group loses access immediately; also reject refresh and consent. A member of another group alone has no access. The existing VerseLink multi-group and invitation flows remain unchanged (`src/server.js` schema around lines 268–290; `/api/orders` around 2185).

## Exact v1 path and domain mapping

The twelve paths below are the OpenAPI paths, including the browser page. Status records distinguish implemented authentication infrastructure from future domain API work. Domain collection reads use v1 cursor paging (`limit` 1..1000, default 500; stable keyset cursor bound to group/filter/scope, invalid cursor `400 INVALID_CURSOR`) and Bearer authentication unless noted; `/me` is a single identity response.

| Method and path | Scope / contract | VerseLink source and mapping | Status / gate |
| --- | --- | --- | --- |
| `GET /.well-known/versekit-org.json` | Public `standard`, `org`, version `1` endpoints and `scopes_supported` | `blueprint_groups.name`; configured public URL; only proven scopes | Planned; publish only with working auth and at least one scope |
| `POST /versekit/v1/device/code` | Public form `client_id`, space-separated `scope`; `device_code`, `user_code`, bare `verification_uri`, `expires_in`, `interval` | Dedicated integration grants; known scope intersection; no invite or telemetry code reuse | Implemented; scope readiness enforced |
| `POST /versekit/v1/token` | Public form device-code or refresh grant; Bearer, `expires_in <= 3600`, rotated refresh, granted `scope` | Dedicated hashed grants/tokens linked to the originating grant, `app_users.id` and fixed group | Implemented; RFC 8628/OAuth errors; replay revokes token family |
| `POST /versekit/v1/revoke` | Public form `token`, optional hint/client; always 200 for unknown token | Dedicated transactional token-family revocation | Implemented; RFC 7009 behavior |

Six and only six standard scopes are `orders:read`, `orders:write`, `stock:read`, `stock:write`, `blueprints:read`, `blueprints:write`. The main application bootstrap currently enables and advertises only `orders:read`; `orders:write` remains unadvertised until the implementation is independently reviewed and explicitly activated. Stock and blueprint scopes remain unimplemented; both snapshot write scopes are unsupported. Basetool Exchange is background comparison only: its DPoP/Keycloak/registry features and other nonstandard client requests are outside v1 and are not inherited into this adapter.

Wire shape checklist for implementers: device-code request is `application/x-www-form-urlencoded` with required `client_id` and space-delimited `scope`; its JSON response requires `device_code`, `user_code`, `verification_uri`, `expires_in` and optionally `interval` (default 5). Token request is form data with either `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `device_code`, `client_id`, or `grant_type=refresh_token`, `refresh_token`, `client_id`; JSON success requires `access_token`, `token_type=Bearer`, `refresh_token`, with optional `expires_in` and `scope`, plus `Cache-Control: no-store`. Revoke requires form `token`, optionally `token_type_hint` and `client_id`, and returns 200 even when unknown. `/me` requires `member.id`, `member.name` and `scopes`, with optional `org.name`/`org.tag`. Stock GET requires `items`; each item requires `item` and nonnegative `quantity`, and may carry `unit`, `quality` (integer 0..1000), `location` and read-only `member`. Stock PUT requires `items` of at most 5000 stock items and returns `items_stored`. Blueprint GET requires `blueprints`; each entry requires `name` and `holders` (string array). Blueprint PUT requires at most 10000 nonempty names of at most 200 characters and returns `blueprints_stored`. Orders GET requires `orders`; every order requires `id`, `title`, `status` (`open/done/cancelled`), and `items`; every item requires `item`, `quantity`, `delivered` and may have `unit`. Delivery POST requires an `Idempotency-Key` header and JSON `{items:[{item,quantity}]}` with at least one positive-quantity item; success is 201 with `delivery_id` and `order`. The three list responses may include `next_cursor` (string or null). Enforce field length limits from OpenAPI for names, locations, notes and keys; do not use this checklist in place of schema-based conformance tests.

## Field, precision and visibility rules

**Orders.** `material_orders.id` is the stable v1 `id`; `title` combines `order_number` and `material_name`. One VerseLink order has one material, so v1 `items` has one entry with the real material name, required quantity, unit, and delivered total. Delivery quantity is the exact PostgreSQL sum when ledger rows exist; otherwise it uses the legacy `delivered_quantity` fallback from `/api/orders`. The two sources are never added together. Write requests reject an order with nonzero legacy progress and no ledger rows; VK-06 does not migrate or reinterpret historical progress. Such orders remain readable and retain their displayed progress. Write quantities are validated against the existing orders decimal precision policy and PostgreSQL compares remaining quantity exactly. For a delivery request with repeated entries for that same material, the exact decimal quantities are summed into one `material_order_deliveries` row; any other material returns `ITEM_NOT_IN_ORDER`. Units map known `SCU`/`CSCU` and piece-equivalent spellings to `scu`/`cscu`/`piece`; unknown units or numeric values beyond 15 significant decimal digits fail the read as `MAINTENANCE` rather than returning a fabricated unit or a rounded quantity. JSON quantities are finite IEEE-754 numbers. Status mapping follows the existing browser normalizer: `cancelled`→`cancelled`, a full delivered total→`done`, and all other statuses (`open`, `claimed`, `reported`, or inconsistent `completed`)→`open`. VerseLink keeps its current report rule: `claimed` and `reported` orders accept deliveries, while `completed` and `cancelled` do not. A partially delivered order remains open in the v1 mapping. The endpoint omits notes, destinations, due dates, quality, assignment, contributor identities and profile data. Neither `location` nor `due` exists on orders. Hidden orders remain hidden and every VerseKit order query includes the configured group (`src/server.js` lines 291–325, 744–752, 2185–2211, 2849–2866).

Orders use descending `(created_at,id)` keyset pagination. The first page captures the newest visible row as a high-water mark; the opaque base64url cursor binds that mark and the last row to the configured group. Inserts newer than that mark do not shift subsequent pages, and a stable UUID breaks timestamp ties. Each page reads from one PostgreSQL repeatable-read transaction while the VK-04 authorization locks remain held. Values may still reflect changes committed between pages (for example, a delivery); the cursor is a traversal boundary, not a multi-request historical snapshot. `limit` defaults to 500 and accepts 1–1000; malformed limits return `INVALID_REQUEST`, malformed or group-mismatched cursors return `INVALID_CURSOR`.

**Stock.** Group stock is a ledger, not a member's personal inventory. Existing `materialInventoryNetRows` groups by member, case-insensitive material name, band, exact quality and source location and subtracts withdrawals; its `Number(...)` arithmetic is a precision risk requiring SQL numeric/keyset verification (`src/server.js` lines 387–403, 2646–2677). Export positive net quantities only, in `scu`, with `quality_value` 1..1000 (the standard also accepts zero, but VerseLink has no zero quality), `source_location` only when present, and a member identity allowed by the agreed visibility policy. `reported`, `deposited` and `in_refinery` cannot be represented as stock fields; decide which states count as shareable before claiming conformance. The group matrix currently aggregates away member, quality and location, so it cannot directly serve v1. The separate `user_inventory` uses integer `quantity`, item catalog UUID/name, location UUID/name, trade status and privacy settings (`PRIVATE/GROUPS/PUBLIC`); it is not automatically group stock. Never export private personal inventory merely because two users share a group. The chosen stock read source needs owner consent and explicit privacy tests (lines 552–589, 1949–1992, 2755–2776).

**Blueprints.** SCMDB is the ownership source: `member_blueprints(token_hash,tag)` plus connected/unrevoked `scmdb_connections`, `app_users`, configured group membership, and optional `reference_blueprints.product_name`. Use stable tag internally for deduplication, but v1 exposes only `name` and holder strings. Decide deterministic English display name and collisions among tags; do not invent a VerseKit blueprint ID. Holders use active group member display names only and respect visibility policy. Existing `accessibleBlueprintQuery` permits *any* shared group; it must not be reused unmodified for the fixed-group adapter. `publicBlueprintQuery` has a fixed-group join but lacks the connected/revoked filter, so also needs adaptation. No SCMDB sink token is a VerseKit credential (`src/server.js` lines 452–511, 1170–1213, 1350–1380, 1925–1932).

## Device grant, errors and threat model

The user enters the existing host, selects Connect, receives a temporary code from VerseLink, opens `/device`, logs in through the existing VerseLink session, types the code, and approves individually selected requested scopes. No registration or automatic consent. The server stores only keyed hashes of random device/access/refresh secrets (and a slow hash or keyed lookup plus attempt limits for the short user code), grant state, requested/granted scopes, immutable user/group binding, expiry and rotation/revocation timestamps. Use a transaction and row lock for one-time code exchange and refresh rotation; concurrent/replayed refresh invalidates the token family. Device code expires (proposed 600 seconds), polling begins at `interval` (default 5 seconds) and increases on `slow_down`; access tokens live at most 3600 seconds. Refresh and any grant extension recheck token validity, revocation, active account, current membership, enabled configuration, granted rights, and the stored group against the configured group. A group switch cannot transfer authorization; old grants are denied immediately and the new group requires fresh consent. Revocation of a refresh token ends its access tokens. Use separate integration-only tables; do not reuse `auth_tokens`, `dashboard_sessions`, `telemetry_pairing_codes`, `group_invites`, or `scmdb_connections` as VerseKit token/grant storage. Existing `dashboard_sessions` remain the browser login session for the approval page.

The confirmation GET has no code in URL. Form POST requires the existing authenticated session, same-origin/CSRF token, deliberate scope selection, fixed-group membership and active account. Escape displayed org/member text. Rate-limit code creation, polling, manual code attempts and token operations by safe client key plus code/grant/account as appropriate; avoid relying on untrusted forwarding headers. Protect against user-code guessing, phishing via forged origin, cross-group data leakage, refresh replay, scope escalation, idempotency replay and log leakage. Log request ID, outcome and opaque grant ID only; never log user/device codes, tokens, cookies, inventory detail or personal notes. Retain/purge grants under a documented period. `verification_uri` must be bare; never put the user code into it. TLS termination at Cloudflare/reverse proxy must preserve the configured public HTTPS origin.

API errors use `application/problem+json` with `status` and stable `code` from the OpenAPI set: `UNAUTHORIZED`, `SCOPE_MISSING`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `INVALID_BODY`, `INVALID_CURSOR`, `IDEMPOTENCY_KEY_MISSING`, `ORDER_CLOSED`, `ITEM_NOT_IN_ORDER`, `RATE_LIMITED`, `MAINTENANCE`, `INVALID_REQUEST`; use `WWW-Authenticate: Bearer error="invalid_token"` on 401 and integer `Retry-After` on 429/503. Device/token grant failures use form-OAuth JSON errors (`authorization_pending`, `slow_down`, `access_denied`, `expired_token`, `invalid_grant`, `invalid_scope`, `unsupported_grant_type`), not problem JSON. Unknown scope names are dropped at device-code creation; if none remain, return `invalid_scope`. Unknown fields are ignored as the v1 contract specifies. Validate method, content type, body size and schema. Do not advertise a scope with placeholder responses.

VerseKit delivery writes use a persistent idempotency row keyed by configured group, authenticated member, and a keyed hash of `Idempotency-Key`. The fingerprint includes the canonical order ID and request body. A successful 201 delivery or deterministic order-level error is stored in the same transaction as the idempotency reservation; matching retries replay that original response after process restart, even if order state later changes. Transient authorization and infrastructure failures are not stored. A mismatched order or body returns `400 INVALID_REQUEST` without replacing the original response or creating another delivery. This table is adapter metadata, not a delivery ledger. The transaction authorizes with VK-04 locks, reserves/checks the key, locks the order, validates group visibility, status, item and remaining quantity, inserts through the shared order operation, and commits the response. Over-remaining requests use `400 INVALID_REQUEST`; closed/cancelled orders use `409 ORDER_CLOSED`; an item mismatch uses `422 ITEM_NOT_IN_ORDER`. Browser claim/report/complete/cancel/hide actions now re-read under the same order row lock. Browser reports preserve the existing active-status rules and completion notification. Nonzero legacy progress without ledger rows is rejected with a conflict in both report paths; it is not rewritten. Despite the handler implementation, the main application bootstrap continues to pass only `orders:read`, so discovery and consent cannot grant `orders:write` until a separate activation review.

## VK-02 foundation status

The VK-02 implementation adds an exact, case-sensitive opt-in: `VERSEKIT_ENABLED=true`. Every other value, including an absent flag, leaves the adapter unloaded and VerseLink routes/startup unchanged. When enabled, `VERSEKIT_GROUP_ID` must be one existing UUID in `blueprint_groups` and `VERSEKIT_PUBLIC_URL` must be an explicit HTTPS origin with no credentials, query, fragment or path beyond `/`. Validation checks the original authority before URL parsing: empty or zero ports, legacy/ambiguous IPv4 spellings, encoded separators and malformed hostnames fail. Conventional IPv4, bracketed IPv6 and valid DNS/IDN hosts are accepted; hostname case and IDN are canonicalized, an explicit default `:443` and optional trailing slash are removed, and other valid ports are retained. Validation and group lookup finish before the server listens; invalid settings stop startup. Public URLs come only from this configuration, never request headers. No new schema, token handling or background job is introduced.

At the VK-02 phase boundary the adapter reserved root `/.well-known/versekit-org.json`, `/versekit/v1` and its descendants, and `/device` only while enabled. VK-02 had **zero operational scopes** and all reserved routes returned 404. VK-03 added device authorization, browser consent, token lifecycle and `/me`, while keeping operational data scopes disabled. VK-05 supersedes that phase boundary by explicitly enabling the implemented `orders:read` scope in production startup. Runtime environment variables still cannot activate additional scopes. Adapter errors are bounded to reserved routes; a fatal Node.js process failure remains a shared-process risk.

VK-02 tests cover disabled mode, strict configuration, group existence, the discovery builder, reserved routing and unavailable endpoints. When `TEST_DATABASE_URL` points to the guarded loopback `verselink_test` database, the integration test creates a disposable schema, uses the real `blueprint_groups` table and spawned HTTP server, verifies enabled and disabled routing, and checks failed enabled startup. It skips locally when no test database is configured; the existing PostgreSQL CI service supplies one. Later phases must add real-client, reverse-proxy/Cloudflare and contract tests before advertising capabilities.

## VK-03 authentication implementation status

At the VK-03 phase boundary, optional OAuth infrastructure left all operational data scopes disabled. `VERSEKIT_ENABLED` must be the exact string `true`; the enabled adapter validates one existing configured group and initializes only VerseKit-specific tables. There is no environment setting that enables capabilities. VK-05 passes the hard-coded `orders:read` capability from production startup after adding its route and tests; other capability values are rejected by the adapter. When VerseKit is disabled, no operational scope is initialized.

Device authorization uses random device/user codes and stores only purpose-separated HMAC hashes. The existing VerseLink `bp_session` and active `app_users` account authenticate `/device`; code entry is POST-only, rate limited, CSRF and same-origin protected. Consent displays only requested capabilities enabled on that adapter, starts with all permissions unchecked, and binds a single-use approval challenge to the member and browser-session hash. Approval or denial locks the challenge and grant rows, revalidates active account and configured-group membership, and performs a one-time state transition. No device or bearer credentials are displayed in the browser.

Token families retain the originating device-grant ID, fixed client, member, configured group and approved scope subset. Access and refresh tokens are stored as keyed hashes. Refresh uses a transaction and row locks, rotates the refresh credential, preserves scopes, and rechecks grant, account and group state. Concurrent or replayed refresh use cannot issue two successful rotations; use of a consumed refresh token revokes the family. `/versekit/v1/revoke` follows public-client RFC 7009 behavior: unknown credentials return an empty 200 response, while a known access or refresh token revokes its complete family and all family tokens transactionally. `/versekit/v1/me` authenticates only with a VerseKit Bearer access token, verifies the originating consumed grant and live token, account, group and membership on every request, and returns only member ID/name, configured organization name and stored approved scopes. Browser cookies do not authorize it.

All VerseKit form endpoints (`POST /versekit/v1/device/code`, `/versekit/v1/token`, `/versekit/v1/revoke`, and browser `POST /device`) share an 8 KiB maximum body and a 10-second total body-reading deadline. An oversized declared `Content-Length` is rejected before reading; a streamed body is rejected as soon as it crosses the limit. These cases return HTTP 413 with `Connection: close`; stalled bodies return HTTP 408 with the same close behavior. The reader pauses request consumption, flushes the response, then closes the socket, so rejected uploads are not drained and the connection is not reused. Client disconnects and stream errors settle the pending read without parsing or changing grant/consent state; request timers and data listeners are cleared. The limit, deadline and behavior apply only to VerseKit form endpoints; they do not change global VerseLink HTTP timeouts. Form content type, duplicate-field checks, CSRF, same-origin, session and rate-limit checks remain enforced.

Requests rejected before form parsing (including unsupported methods, unexpected query strings, invalid consent origins and rate limits) pause the unread request, return the existing rejection with `Connection: close`, then close the socket after the response flushes. A bounded fallback closes connections if response flushing fails; rejected uploads are never drained or reused.

Device-grant storage is capped globally at 10,000 retained grants. Every creation transaction takes the same PostgreSQL transaction-scoped advisory lock, counts all retained grant states, and inserts only below the cap. Capacity exhaustion fails closed with OAuth `temporarily_unavailable`, HTTP 429 and `Retry-After: 900`; cleanup frees capacity under the same lock coordination as new admissions. The limit applies across adapter instances sharing the database and is not environment-configurable.

VK-03 supplies authentication and connection lifecycle only. VK-04 remains responsible for the broader central authorization/scope enforcement layer; VK-05, VK-07 and VK-08 must implement and test individual data scopes before any are advertised. VK-06 remains conditional and is not required for the read-only MVP. VK-09 remains responsible for real-client, conformance and DEV validation. No deployment, image publication, discovery activation or business-data endpoint is implied by this implementation status.

Credential retention: token families have a fixed 180-day absolute lifetime; refresh never extends it and credentials expire no later than that boundary. Family/grant/token history is retained until seven days after family expiry to preserve refresh replay detection, then the family cascade removes its credentials. Orphanable expired pending, denied, or consumed grants are retained 30 days. Consent challenges are removed one day after expiry or consumption. Expired access-token rows are independently eligible for removal. The enabled adapter schedules cleanup every 15 minutes, in batches capped at 200 rows per record category, using PostgreSQL `SKIP LOCKED` and transactions so multiple instances can run safely. Runs do not overlap within an instance; failures are caught and retried by the next interval with only safe error metadata logged. Disabled mode creates no VerseKit tables or cleanup timer. Active refresh tokens and families are not cleanup candidates.

## Global device-grant admission and retained storage

Enabled instances sharing PostgreSQL use one persistent global token bucket: production capacity is 24 grants, refilled continuously from PostgreSQL time at one token per 3600 seconds. Initialization persists capacity and refill interval; later initializations validate the stored policy and fail on conflict without resetting balance or timestamp. Grant creation takes a PostgreSQL transaction-scoped advisory lock, refills and consumes a token, checks the global retained-grant count, then inserts within the same transaction. Failed admission rolls back token consumption. The existing per-IP limiter is additional protection, not a substitute for the database-wide limit. At most 10,000 retained device grants are admitted. HTTP capacity rejection returns 429, `Retry-After` (900 seconds for the storage ceiling; a calculated positive delay for an empty bucket), and `temporarily_unavailable`.

Cleanup can restore storage capacity: expired orphanable grants are eligible after 30 days beyond grant expiry; a grant referenced by a retained token family remains until family cleanup. Cleanup runs every 15 minutes in bounded batches. Disabled mode does not initialize the adapter, quota table, or cleanup job.

### Availability limits and retention estimate

The shared bucket is a finite availability resource: an attacker who can reach the endpoint can exhaust its current balance and temporarily prevent legitimate new device authorizations until refill. This does not invalidate existing access tokens or make refresh and revocation depend on new-grant admission; those operations do not consume new-grant tokens. The bucket and IP limiter reduce abuse but do not eliminate denial-of-service risk.

For a healthy-operation estimate, a grant can exist for up to 10 minutes before its token family is created. The family then has a fixed 180-day absolute lifetime, followed by seven days of replay-history retention and at most 15 minutes until scheduled cleanup: approximately 187.0174 days total. At one grant per hour, plus the initial 24-token burst, a conservative estimate is `24 + ceil(24 × 187.0174) = 4,513` retained grants. Orphanable grants have the shorter bound of a 10-minute grant lifetime, 30 days post-expiry retention, and up to 15 minutes of cleanup delay; at the same issue rate this is below the family-backed estimate. This estimate assumes cleanup continues to run and no administrator or other process disables it. It is not an absolute database-size guarantee: prolonged cleanup outages, operational changes, or unusual retained records can allow storage to grow until the 10,000-grant admission ceiling rejects new grants.

## Upstream v1 compatibility: capacity errors

The reviewed upstream contract is the VerseKit v1 OpenAPI at [the pinned upstream revision](https://github.com/Xharig/VerseKit/blob/10438c39aa1fb6bd4901483c51b4ce5b4d00bf9f/tools/orga-standard/v1/openapi.yaml) (blob `10438c39aa1fb6bd4901483c51b4ce5b4d00bf9f`). The contract's general API description mentions HTTP 429 and 503 with `Retry-After`; the device-code operation explicitly lists 200 and 400, and its `OAuthError` enum does not include `temporarily_unavailable`.

Accordingly, the implementation's 429 status and positive `Retry-After` align with the general error guidance, but `{ "error": "temporarily_unavailable" }` is outside the published enum, and 429 is not explicitly listed among that operation's responses. A strict schema-validating client may reject either discrepancy. The other listed OAuth errors are not suitable substitutes: `invalid_request`, `invalid_scope`, and grant-state errors would misrepresent a temporary capacity condition. This is a confirmed schema mismatch; client rejection is a compatibility risk inferred from strict validation, not a demonstrated behavior of every client. Resolve it through an upstream specification clarification or explicit extension before claiming full conformance. Keep the current response documented as a known compatibility limitation; it does not by itself block VK-03 commit approval, but it must be addressed before claiming strict contract conformance or enabling broad discovery.

## VK-04 centralized authorization and revocation

VK-04 reuses the VK-03 token, family, grant, account, group, and membership records. Its centralized `VersekitTokenStore.authorizeAccess` guard is the authorization entry point for protected adapter handlers. It accepts a Bearer credential and an adapter operation name; it has no group argument. `VERSEKIT_GROUP_ID` remains the only group authority. A successful authorization requires an unexpired and unrevoked access token and family, a consumed grant whose member, group, and approved scopes still match the family, an active `app_users` account, an existing `blueprint_groups` row, a current `group_members` row, the currently configured group ID, and scopes that remain enabled by the trusted adapter capability set. `/me` has no scope requirement. Data handlers pass their required operation scope to this guard; unknown or unimplemented capabilities are denied. VK-05 configures only `orders:read`, and discovery advertises that scope only.

The adapter never receives group selection from a request. It does not inspect a user's other memberships, owner role, or administrator flag when authorizing. Every token and grant stays bound to the configured group. Removing membership, changing account status, deleting the group, or changing the configured group makes subsequent authorization or refresh fail closed. The existing VerseLink group, invitation, and ownership workflows are unchanged.

The smallest persistent addition for group reconfiguration is the VerseKit-only singleton `versekit_authorization_config` marker. `VERSEKIT_GROUP_ID` remains authoritative; the marker records which configured group currently owns active credentials across adapter restarts. A group change is durably observed when an enabled adapter activates the new group. A transition A → enabled B revokes all existing token families and denies pending or approved device grants in the same PostgreSQL transaction before updating the marker. B → enabled A performs the same invalidation, so historical A tokens cannot reactivate. A normal restart with the same configured group leaves the marker and eligible credentials unchanged.

Disabling VerseKit is an operational pause, not an implicit permanent revocation event. While disabled, its routes are unavailable, no VerseKit authorization runs, and no VerseKit schema, background job, or configuration-marker update is performed. Re-enabling the same configured group may preserve otherwise valid credentials. An intermediate group setting that is present only while the adapter is disabled is unobserved: for example, A → disabled with B configured → disabled with A configured → enabled A may preserve the original A credentials. Environment changes made while no adapter is running cannot be detected retroactively. A policy requiring unconditional revocation across such unobserved changes needs a separate persistent configuration-generation mechanism or an explicit administrative revocation event; neither is provided here. Use the explicit token/device revocation mechanism when a permanent disconnect is intended.

The marker is not a general configuration store and contains no user-controlled selection. All replicas sharing a database must use the same `VERSEKIT_GROUP_ID`. A stale instance whose ID no longer matches the marker fails closed for new grants, consent, exchange, refresh, and access authorization; differently configured replicas can repeatedly invalidate each other's credentials and are unsupported.

Protected request errors follow Org Standard v1: absent or invalid credentials return HTTP 401 `UNAUTHORIZED` with `WWW-Authenticate: Bearer error="invalid_token"`; an otherwise valid credential without the required grant returns HTTP 403 `SCOPE_MISSING` with `WWW-Authenticate: Bearer error="insufficient_scope"`. Both use `application/problem+json` and disclose no group or credential details. Device authorization, refresh, and revocation retain their existing OAuth responses.

The guard runs in a short PostgreSQL transaction and locks token, family, grant, user, group, and membership rows while it validates them. This linearizes request-start authorization with concurrent membership removal, account deactivation, group deletion, and family revocation: a change that commits first denies the request; a request that obtains the locks first completes its authorization before the change commits. The transaction ends before `/me` writes its small response. Future write handlers must begin their own transaction, invoke the guard before taking domain locks, and keep the same transaction open through the protected domain query or mutation. They must apply `group_id = VERSEKIT_GROUP_ID` to every domain query. Lock the authorization marker first, then keep the VK-03 order (`configuration marker → token → family → grant → identity/group membership`); keep transactions limited to database work and do not carry locks across network calls or response streaming.

### VK-04 implementation gap matrix

| Requirement | VK-03 protection | VK-04 gap | Minimal correction | Regression coverage |
| --- | --- | --- | --- | --- |
| Central request authorization | `/me` used one live token/account/membership query | Logic was route-specific and the lookup held no row locks | Add `authorizeAccess`, shared problem mapping, and transaction-scoped row locks | Valid, invalid, expired, revoked, and scope-denied guard cases |
| Fixed group and principal status | Tokens and grants stored one group; query joined active user and membership | No durable configuration-change invalidation; stale adapters could issue grants | Add one VerseKit authorization marker; require its active group in eligibility and access queries | A → B → A revocation, stale adapter, multi-group fixture |

## VK-05 fixed-group Orders read

Only the literal configured group is read, and rows with `hidden_at IS NOT NULL` are excluded. Before exposing discovery or OAuth capabilities, startup scans visible Orders for that group using the same `mapVersekitOrder` mapper used by the endpoint. If any row cannot be represented, the adapter stays unmounted and `orders:read` is not advertised; VerseLink continues serving its ordinary routes. Invalid group/public-URL/secret configuration and other adapter initialization errors retain their existing fatal startup behavior. A restart reruns readiness.

The v1 unit map is explicit: `SCU` → `scu`; `CSCU` → `cscu`; and `piece`, `pieces`, `pc`, `pcs`, `item`, `items`, `unit`, `units`, `qty`, `stk`, `stück`, and `stueck` → `piece`, case-insensitively after trimming. Quantities must be nonnegative decimal values with at most 15 significant digits, a finite JSON `Number` representation, and a normal (not subnormal) binary magnitude when nonzero. Before conversion, the source decimal is retained and compared exactly with the shortest decimal that round-trips to the candidate JSON number. This accepts ordinary values such as `0.1`, `0.25`, and `12.5`, while rejecting material conversion loss, subnormals, and nonzero values that underflow to zero. Exact zero remains valid where the source field allows it. This policy accounts for the distinction between PostgreSQL's exact `numeric` decimal and JSON's IEEE-754 binary number; it does not require every decimal to have an exact binary representation. Delivered quantity is the exact sum of delivery ledger rows whenever any exist; otherwise the legacy `material_orders.delivered_quantity` value (or zero) is used. Completion status is decided by scale-aware exact decimal comparison of the original required and delivered values, never by comparing rounded JSON numbers. Required identifiers, order number, material name, supported status, and canonical creation timestamp are validated. This is a read-side compatibility gate only; browser Orders validation and stored business data are unchanged.

The readiness transaction locks the configured group parent first, then scans its visible orders in bounded ID batches under repeatable read. This follows the VK-04 parent-before-child authorization/deletion ordering; the parent lock also serializes inserts protected by the group foreign key while the scan runs. It does not lock order rows or unrelated groups, and it performs no writes to business data. A hidden or other-group unsupported order does not block startup.

Each continuation cursor is canonical JSON encoded as base64url plus an HMAC-SHA256 signature. A cursor-only key is derived from `VERSEKIT_TOKEN_PEPPER` with the context `verselink:versekit:orders:cursor:v1:key`; the MAC separately authenticates the payload with the `verselink:versekit:orders:cursor:v1` context. Cursors contain an explicit version and bind the fixed group, `orders:read`, high-water tuple, and last returned tuple. MAC comparison is constant-time; noncanonical encoding, invalid MAC, wrong group/scope/version, invalid timestamps/UUIDs, and impossible descending tuple order return `400 INVALID_CURSOR`. Timestamp precision retains PostgreSQL microseconds so equal creation times continue deterministically by UUID.

## VK-10 independent signing key and operations

`SINK_TOKEN_PEPPER` remains the stable key for existing VerseLink and SCMDB functionality, including sink/auth/recovery tokens, dashboard sessions, group invites, telemetry credentials, and public-link hashes and ciphertext. Do not rotate it to enable or operate VerseKit. VerseKit uses only `VERSEKIT_TOKEN_PEPPER` for device/user-code hashes, consent challenges, consent CSRF/session binding, access/refresh hashes and revocation lookups, and Orders cursor signing. Existing purpose-separated HMAC labels and cursor contexts remain unchanged. There is no fallback or dual-key verification.

The new key is read and validated only when `VERSEKIT_ENABLED` is exactly `true`. It must contain at least 32 UTF-8 bytes. Generate a separate random key for each environment (for example `openssl rand -hex 32`); use independent DEV and PROD values, store/backup them securely, and keep each stable. All replicas sharing one database must use the same VerseKit key.

### First activation and legacy credential cleanup

Before first activation of VK-10 on an installation where VerseKit may have issued credentials under the former shared key, quiesce every VerseLink application instance. **Stopping incoming VerseKit HTTP traffic alone is insufficient:** an enabled adapter also runs its 15-minute credential cleanup timer, which can overlap this standalone procedure.

For Compose/Portainer deployments, set `VERSEKIT_ENABLED=false` on every app instance and redeploy/restart every replica, or stop every VerseLink app container. Confirm all hosts/nodes and Portainer replicas have replaced the old process; an old enabled instance must not remain running. A disabled process does not mount the adapter and starts no VerseKit cleanup timer. The operator must verify the all-instance state because the database does not record a reliable live-instance/adapter lease, and an advisory lock used only by this script would not coordinate with the application's existing timer.

Before applying, verify the intended database target in the operator's secret manager/Portainer configuration without printing `DATABASE_URL`; verify each active VerseLink instance is disabled or stopped; and verify no old container/replica remains. Then run the read-only assessment:

```sh
node scripts/versekit-legacy-credentials.js --dry-run
```

Dry-run is read-only and safe to repeat; it reports only VerseKit row counts. Review its output and confirm the expected installation and impact. Applying is destructive to existing VerseKit authorization state: active token families/tokens are revoked, pending/approved grants are denied, and live consent challenges are expired. Audit rows remain. Never apply it to DEV or PROD unless that environment has separate explicit cleanup authorization.

Only after the quiescence and target checks above, explicitly apply:

```sh
VERSEKIT_ENABLED=false node scripts/versekit-legacy-credentials.js --apply --confirm-versekit-only-revocation --confirm-all-versekit-instances-quiesced
```

The CLI refuses apply unless its environment explicitly has `VERSEKIT_ENABLED=false` and both confirmation flags are present. This catches an accidental apply from an enabled deployment shell. `--confirm-all-versekit-instances-quiesced` is an operator attestation, not automatic cluster discovery: check every node/replica before using it. The script still cannot detect an independently running app instance. Dry-run is the default and opens a read-only transaction. Apply opens one transaction, locks the configuration marker and all referenced group parents before VerseKit child rows in VK-04-compatible parent-first order, then revokes active families/tokens, denies pending/approved grants, and expires unconsumed challenges. It retains grant, family, token, and challenge rows as audit/retention history. If no VerseKit schema exists, it reports a no-op; a partial schema fails without changing rows. It never reads either pepper and never writes VerseLink/SCMDB credential tables or business data. The manual and scheduled cleanups have different child-row lock orders; quiescing all enabled adapters removes that overlap. No DEV or PROD cleanup is performed by this code or automatically at startup.

Changing the VerseKit key makes previously issued device and user codes, consent/CSRF challenges, access/refresh tokens, and cursors fail under the new key. Old access tokens are rejected; old device exchanges and refreshes fail closed. A new-key revocation request cannot locate an old-key token row, which is why the one-time cleanup is recommended before a key change when legacy credentials may exist. The cleanup also prevents a rollback to old code plus the unchanged Sink pepper from reactivating legacy VerseKit grants. After activation or any key rotation, clients must reconnect; old cursors return `400 INVALID_CURSOR`.

For rollback, restore the prior image and its prior settings with `VERSEKIT_ENABLED` unset or `false`; keep `SINK_TOKEN_PEPPER` unchanged. Do not roll back to the old image with VerseKit enabled after legacy cleanup. Re-enable VerseKit only with a deliberate key choice and fresh client consent.

An unsupported row introduced after startup causes the complete affected collection request to return generic `503 MAINTENANCE` with `Retry-After`; it is never rounded, omitted, or returned partially. One incompatible visible row can therefore make every page fail until the source data is corrected, because silently skipping it would make the collection incomplete. Subnormal source values and decimals whose shortest JSON-number round-trip differs materially from PostgreSQL's exact value use stable reasons such as `REQUIRED_QUANTITY_PRECISION_UNSUPPORTED` or `DELIVERED_QUANTITY_PRECISION_UNSUPPORTED`; nonzero values that become zero use the corresponding `*_PRECISION_UNDERFLOW` reason. Logs do not include order identifiers, content, user information, or credentials, and are throttled per reason. Operators should inspect visible Orders for the configured group in VerseLink, correct the unit or quantity through the existing authorized Orders flow (or hide the row if it should not be published), and retry; a row made compatible after startup recovers without restart, while startup-blocking data requires restarting to rerun readiness.

The device-code capacity response's `temporarily_unavailable` remains outside the published OAuth error enum. The reviewed stock client handles non-200 device-code responses by HTTP status and does not parse that response body, so no client failure has been demonstrated. This remains a separate, nonblocking strict-schema compatibility observation; no OAuth behavior is changed in VK-05.
