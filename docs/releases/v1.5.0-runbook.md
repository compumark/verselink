## Publication preflight — requires explicit approval before executing

1. Review and approve the text in `docs/releases/v1.5.0.md` (including #129 and the unverified Blueprint-holder check).
2. In a **separate release-finalization PR**, add the approved bullets to `public/changelog.html` as a new **stable** `1.5.0` entry with the actual release date; update outdated current-stable references if needed. This entry must be in the **same final source commit** used for the tag and stable image.
3. Squash-merge that PR only after final review and all CI/CodeQL checks are green. Include `[release-changelog]` in the squash commit message to avoid a premature `Changelog to Discord` push notification.
4. Freeze `main`. Record its full commit SHA as `RELEASE_SHA`, confirm `public/changelog.html` contains `data-release-kind="stable" data-version="1.5.0"`, confirm `v1.5.0` does not already exist, and recheck final CI.
5. Verify that a PostgreSQL backup and secure Portainer environment/volume-path backup plan for PROD are available; inspect potential schema effects and rollback for the exact source revision.
6. After **separate explicit publication approval**, create `v1.5.0` pointing exactly to `RELEASE_SHA`; run the existing `Publish Docker image` workflow with `ref=main`, input `release_version=1.5.0` **only while main still equals RELEASE_SHA**.
7. Verify the workflow succeeded and `ghcr.io/compumark/verselink:1.5.0` is published; inspect the immutable digest and image metadata. The tag, `APP_COMMIT` and `RELEASE_SHA` must agree. Check companion tags `1.5`, `1`, `latest` point at the published stable build.
8. Publish the GitHub Release `v1.5.0` using the reviewed notes. The existing `Changelog to Discord` release event sees the already-present 1.5.0 changelog entry, skips creating an extra commit/automatic second image build, and then posts to Discord. Verify its result; do **not** publish the GitHub Release before the stable image is checked.
9. Production deployment is a **third separate approval**. Pin `:1.5.0` or the verified digest in Portainer, preserve the original PostgreSQL volume and environment, deploy, and verify login, health, Orders, Groups, Missions, SCMDB, VerseKit opt-in scope and telemetry privacy.

## Why this order matters

`.github/workflows/changelog-discord.yml` currently creates a new changelog commit and dispatches a stable image build *only when a published release does not yet have a changelog entry*. If the entry already exists, it returns without building. Publishing the release first therefore risks making `v1.5.0` point at a different commit from its stable image, or not creating the expected image at all. The controlled **changelog → freeze → tag → explicit stable build → publish GitHub Release** order avoids this mismatch without changing existing automation.

**Do not** run `workflow_dispatch` for `docker-publish.yml` until the final tag and commit have been approved. Because that workflow also moves `latest`, this is a public stable publication action.
